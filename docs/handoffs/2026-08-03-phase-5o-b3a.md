## Accepted B3 contract

ADR 0044 and Phase 5O-B3 establish these implementation constraints:

- Exact `GET`, `HEAD`, and `OPTIONS` route: `/v1/models/{id_or_slug}`. Reject a query marker, body, trailing slash, or extra segment.
- Stable IDs and current slugs return the canonical `200` representation.
- An unpinned historical slug returns a bodyless relative `308` to the stable-ID route.
- An explicitly publication-pinned historical slug returns the exact pinned publication's canonical `200`; it does not redirect through the current publication.
- Only stable-ID requests may use the manual Cache API, after validation, both limiter buckets, and resolver V2.
- Pre-invocation Workers Caching remains disabled with `cache.enabled: false`.
- Stable-ID public responses use `private, max-age=0, must-revalidate`. Slug, redirect, error, query, and OPTIONS responses use `private, no-store`.
- The internal manually cached object uses `public, max-age=300, must-revalidate`; this policy must not leak to the public response.
- Strong ETags cover the exact response bytes.
- The complete public `ModelDetail` representation must not exceed 65,536 UTF-8 bytes.
- A pre-open audit and the only authorized activation/rollback application path must reject any serveable publication containing an oversized Model detail.
- Do not persist an admission receipt.
- The public path stores no visitor information and emits no cookies, logs, traces, request metrics, analytics, correlation IDs, or other custom visitor telemetry.

## B3A component map

### API/query adapter

The query-side V2 reader is already implemented and tested in `apps/query/src/model-detail.ts`. Leave its publication-pinned resolver and storage semantics unchanged.

Add a strict API-side V2 adapter, following the V1 hostile-output boundary in `apps/api/src/model-detail-query.ts`:

- Add `ModelDetailApiV2Input`, `ModelDetailApiV2Outcome`, and `readModelDetailFromQueryV2`.
- Parse only an exact lowercase Model stable ID or a strict slug.
- Require the result's own keys to be exactly `lookupProvenance`, `model`, `outcome`, `publicationId`, and `schemaVersion`.
- Require provenance keys to be exactly `matchedBy`, `canonicalSlug`, and `projectionVersion`.
- Require the expected publication, schema semantic version, and projection version `model-slug@1`.
- For a stable-ID input, require `matchedBy === "stable_id"` and exact Model identity.
- For a slug input, allow only `current_slug` or `historical_slug`. A current match must have `canonicalSlug` equal to the submitted slug; a historical match must differ.
- Validate `canonicalSlug` as strict lowercase ASCII, 1–128 UTF-8 bytes, and require it to equal the canonical Model's known slug.
- Reject extra keys, accessors, proxies, malformed prototypes, inconsistent provenance, cross-publication output, and every contract mismatch as an integrity failure.
- Never expose the submitted historical slug or lookup provenance in the public representation.
- Preserve V1 compatibility and its tests.

The relevant existing seams are the RPC types in `packages/api-core/src/index.ts`, the hostile-result parser and V1 adapter in `apps/api/src/model-detail-query.ts`, and the envelope encoder later in that same module.

### Shared representation encoder

Create one exact encoder in `packages/api-core/src/index.ts` and use it for both admission and public delivery. A suitable exported ceiling is `MODEL_DETAIL_PUBLIC_MAX_BYTES = 65_536`.

The encoder must:

- accept a fully normalized canonical Model plus exact publication/schema metadata;
- construct the sole public envelope in fixed insertion order as `data`, then `meta`;
- construct metadata as `resource`, `publication_id`, `schema_version`, `sort`, and `filters`;
- use sort value `["name", "stable_id"]` and empty filters `{}`;
- stringify once and UTF-8 encode once;
- enforce the 65,536-byte ceiling on those exact bytes;
- return or make available the exact bytes used by both the strong ETag and the response body;
- exclude lookup provenance, submitted identifiers, and all non-contract fields.

Keep the current API snapshot's deterministic key normalization aligned with this encoder so admission bytes cannot drift from served bytes. Add exact encoder vectors in API-core tests.

### Activation and rollback admission

The sole current schema-1.13 application switch path is `applyServingSwitchV5` in `apps/pipeline/src/serving-switch-v5.ts`. Its application-level head mutation is the `INSERT_HISTORY_SQL` statement included in the `first-primary` session batch. Insert admission after the switch classifier returns `execute` and after the existing provider/slug proof checks, but before that atomic batch.

A focused module such as `apps/pipeline/src/model-detail-admission.ts` should:

- scan every Model in the target publication using fixed, primary-session, stable-ID-ordered pages;
- keep row count, per-row bytes, total bytes, page count, CPU, and memory explicitly bounded;
- parse and validate each canonical Model with the existing Model contract;
- require exact identity, type, publication, and content hash;
- use the shared public encoder and reject 65,537 bytes while accepting 65,536;
- reconcile the exact Model count with the already verified slug proof;
- fail closed without changing the application head;
- emit no visitor or custom request telemetry and persist no receipt.

Add a separate pre-open audit that enumerates every publication that could be served at the required active/rollback/retained-hot horizon and applies the same guard. Merely making this function callable is not release evidence: a later protected release gate must actually invoke and record the non-visitor control-plane result before opening the route.

Do not retrofit the legacy recovery paths. Current local restore/rebuild code is not a schema-1.13 authority: `serving-restore-rebuild@6` remains future Phase 5O-B2C-B2 work.

Adding the shared encoder to the pipeline likely requires adding `@quant-clarity/api-core` to `apps/pipeline/package.json`, its TypeScript project reference, and the lockfile. Confirm the dependency direction remains acyclic before doing so.

## Unresolved enforcement boundary

This question is intentionally unresolved and must be documented before claiming non-bypass atomicity:

The application identifies `applyServingSwitchV5` as the only authorized head-mutation path, but migration `migrations/serving/0016_model_slug_lifecycle.sql` contains the `publication_switch_history_apply` trigger. A valid direct insert into switch history can therefore cause the database head mutation without executing an application-side representation scan.

Two credible approaches were identified:

1. Define and enforce an application-only, least-privilege threat boundary: deployment identities cannot execute arbitrary D1 SQL, and direct administrative SQL is outside the authorized switching workflow. This needs explicit design and protected configuration evidence.
2. Enforce admission in the database mutation itself. A persisted admission receipt conflicts with ADR 0044, while reproducing exact JSON representation encoding inside a trigger is likely impractical and risks byte drift.

Do not silently choose either approach. Reconcile ADR 0044's “only path” language, D1 operational access, and least-privilege deployment controls in a small design amendment or follow-on ADR before asserting the admission guard cannot be bypassed. No product requirement amendment appears necessary unless the resolution changes accepted behavior.
